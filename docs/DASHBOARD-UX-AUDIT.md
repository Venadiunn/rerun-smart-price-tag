# Dashboard UX and readability audit

This records the initial dashboard audit. The subsequent shadcn theme revision increases the shared type scale by 15%, improves dark-mode separation and borders, and standardizes controls. Current measurements and patterns are documented in [UI-DESIGN.md](./UI-DESIGN.md).

The user-supplied reference, `design principles for dashboard design.pdf`, is a 30-page saved copy of DataCamp's _Effective Dashboard Design: Principles, Best Practices, and Examples_. Its design guidance was treated as reference material. Website navigation, advertisements, course links, and calls to action inside the document were not instructions for this application.

## Applied principles

| Reference principle                                 | Application decision                                                                                                                                                                                        |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Prioritize the next operational decision            | Retain headline counts, then automatic sorting, then the restocking queue and activity. Keep Scan, Receive stock, Review & place, and sorting actions explicit.                                             |
| Use a consistent grid, spacing, and type hierarchy  | Enlarge the shared typography scale and control sizes across every page; let names, metadata, actions, and tabs grow with content.                                                                          |
| Keep the core view focused                          | Retain short summaries, paginated inventory/master data, progressive disclosure, and detailed dialogs. Do not add speculative charts or additional metrics.                                                 |
| Make metrics understandable                         | Preserve units, capacity denominators, count labels, pricing-rule explanations, and simulation boundaries. Do not invent targets or historical comparisons that the application does not store.             |
| Show data freshness                                 | Add the actual last successful fetch time, time zone, manual refresh, and a visible background-refresh failure state.                                                                                       |
| Reserve color for meaning                           | Retain neutral shadcn chrome and existing labeled success, warning, and error states in both themes. Keep text labels and numeric counts alongside the store legend.                                        |
| Support keyboard, touch, and different screen sizes | Enlarge controls, preserve focus states and semantic native widgets, expose scrollable tables to keyboard users, and check dialogs at phone, desktop, landscape, and keyboard-reduced sizes.                |
| Test tasks and iterate                              | Exercise search, selection, review dialogs, navigation, tabs, receiving with a mocked command, and refresh recovery. Check wrapping, page overflow, text enlargement, spacing, and automated accessibility. |

## Design measurements

At the default 16-pixel browser setting: standard body 16 pixels; supporting text 14–15 pixels; desktop page title 28 pixels; phone page title 26 pixels; typical section headings 18–20 pixels. Relative text units support browser preferences. Form fields remain at least 16 pixels to avoid phone input zoom. Primary/default actions are at least 44 pixels in normal use, compact desktop actions at least 40 pixels, and phone actions at least 44 pixels. The 500 capacity markers remain information marks, not individual selectable controls.

## Scope and limits

No database migration, reseeding, credential changes, or inventory mutations are required for this presentation update. Capacity, tag count, product records, staff roles, pricing logic, workbook persistence, stock transitions, and QR payloads retain their existing meanings. The refresh timestamp describes data retrieval, not a physical stock count or tag synchronization. Automated accessibility and layout checks supplement visual review; they do not replace usability sessions with store staff or establish complete accessibility certification.

## Verification

Lint, the production build, and 25 domain tests passed. Across the browser suites, 45 distinct scenarios passed: all nine screens in both themes at 1440, 1024, 768, 390, and 320 pixels; readable text and assigned-product row geometry; selection controls; 200% text enlargement with expanded spacing; refresh recovery and access-error guards; phone location navigation; and shared dialog centering/focus/keyboard behavior. Two checks interrupted during initial data loading passed on rerun. Automated WCAG A/AA checks found no violations on the nine desktop screens in either theme, or on phone sign-in and item dialogs. Compiled-build checks also passed for selection, controls, enlargement, refresh recovery, and representative dialogs. Hosted verification is performed during release.

Durable coverage lives in `tests/readability.spec.ts`, `tests/dashboard-ux.spec.ts`, `tests/selection.spec.ts`, `tests/design.spec.ts`, and `tests/modals.spec.ts`. Private test sessions and screenshots are excluded from version control.

Technical references for refresh error handling: [Supabase JavaScript RPC](https://supabase.com/docs/reference/javascript/rpc), [PostgREST error status mapping](https://docs.postgrest.org/en/stable/references/errors.html).
